- **#330, `JvmStorage`'s writes, lock and open:**
  - §3 `RevoktStorage`: a write whose fsync, directory fsync or rename throws throws; on Windows the directory fsync is
    skipped. `JvmStorage`'s `lock()`, once it holds the lock, deletes every temp file under its root, then fsyncs
    every directory under it, the root included, in place of the three named store directories. The parent of every
    directory it creates is fsynced, the root's included.
  - §3 `names()` excludes every entry whose path is not a key; `JvmStorage` lists regular files only and follows no
    link below its root's real path: a link in a key's path makes it not a key, so `names()` skips it and `read()`,
    `write()` and `delete()` of it throw.
  - §3 `identity()` is the absolute normalised directory, computed with no I/O; `JvmStorage.directory(…)` does no I/O,
    and `lock()` creates the directory.
  - §3 keys are lowercase, `[a-z0-9._-]` segments, so no two keys are one file on a case-insensitive file system and
    no key is `.lock` there.
  - §3 `lock()`: `FileChannel.tryLock` on `.lock`, tried every 100 ms for 1 s; one channel per `.lock` file in a
    process, keyed on its file key, so a failed second attempt through any path to the file, a hard link or a bind
    mount included, cannot drop the holder's fcntl lock; the ownership check runs before `.lock` is opened; `.lock` is
    lstatted first and must be a regular file (a link or a FIFO is `STORE_UNREADABLE`), then opened for reading and
    writing with no link followed; `.lock` is never deleted; any other failure in `lock()` is `STORE_UNREADABLE`.
  - §3 the ownership check compares the directory's uid with a probe file's, a probe that cannot be deleted being
    `STORE_UNREADABLE`, and is skipped without a unix view;
    the root's mode is checked before the probe is written; every directory under the root, in `lock()`'s walk, gets
    the same uid and mode rule, checked before the sweep deletes anything in it.
  - §3 Windows: the rename over an open `current` is retried for up to 1 s, then the write throws.
  - §6.5 temp files: the key's last segment, `~` and 32 random hex digits, with no pid; `~` keeps them out of the key
    space. No link below the store's real root is followed.
  - test-plan.md (e): the `JvmStorage` row names `JvmStorageTest`, `JvmStorageLockTest` and `JvmStorageContractTest`.
- **#330, the store at `start()` and `close()`:**
  - §4 `WarningCode` gains `STORE_UNREADABLE`, `STORE_MIGRATED`, `STORE_NEWER_LAYOUT` and `STORE_LOCKED`, logged at
    `WARN` until 0.3's `state`.
  - §3 `identity()` is read by `start()`, never by `build()`: `JvmStorage`'s is the root's file key, or its real path
    where the file system has none, read after creating the root, so a link, a bind mount or another spelling meets
    one registry entry; a failure is `STORE_UNREADABLE`. `isEmpty()` joins the members: no entry in the root but
    `.lock` and temp files. `JvmStorage.directory(…)` still does no I/O.
  - §3 keys: no segment is `.lock`, and `store.version` is a key only as the whole key; `JvmStorage`'s `names()` and
    open walk enter no directory below the root that holds a `.lock`, so a store nested in another keeps its files.
  - §5.1 `start()`: a second instance on one store throws `IllegalStateException` before any lock is taken; a malformed
    or unreadable `store.version`, or none beside other entries, is `STORE_UNREADABLE`; a `start()` that throws after
    the lock and before its loader runs releases it and deregisters the identity, and once the loader runs only
    `close()` releases them. `close()` releases both after the loader's exit and before `engine.close()`; if stopping
    the loader throws, the lock stays held and a later instance on that store in the process throws.
  - §6.5 `store.version`: ASCII decimal `[1-9][0-9]{0,8}`, read after the open's temp sweep; empty means no entry but
    `.lock` and temp files. A non-empty store with no `store.version` is no longer rebuilt: it is `STORE_UNREADABLE`,
    in memory and untouched, as is one that does not parse or whose read throws. The rebuild deletes every other key
    first and writes `store.version` last, so a failed or interrupted rebuild keeps the old version and runs again at
    the next start; a delete or write of it that throws is `STORE_UNREADABLE`.
  - test-plan.md (e): the store-step items (`StoreOpenTest`, `CrliteRuntimeStoreTest`, `RevoktStoreTest`); §9.1 adds
    `store.version` to the store readers (`StoreVersionFuzzTest`).
