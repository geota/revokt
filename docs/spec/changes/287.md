- **#287, the content-addressed store:**
  - §6.5 layout: `<dataset>/<channel>/blobs/<sha256>` holds every attachment, full or delta, under its signed SHA-256.
    `generations/<sha256>` holds one generation file per generation, named by the SHA-256 of its own bytes:
    `generationVersion`, `dataset`, `channel`, `freshness`, `seedFormat` (a seed's only), `signature`,
    `signerLeafSha256` and the verified `records`. Everything else is derived at load. `current` names generation
    files. The generation directories, `meta.json`, a stored `index.bin` and `records.json` go.
  - §6.5 the generation file's cap is the configured `maxJsonBytes` plus 64 KiB, checked before the write and at every
    read. An install over it is `FAILED` with `STORE_FAILED`, counted, and logged naming the cap.
  - §6.5 Load: one function for the recovery chain, an install's load-back and the adopt scan. It re-hashes the
    generation file against its name and every blob against its record, then rebuilds `index.bin`.
  - §6.5 install order: the blobs, `index.bin`, the format check, the generation file, the load-back (keeping the index
    just built), `prepare`, `activate`, publish, the flip, `updater.json`, prune. A failed install deletes nothing. The
    delta base and parent are the served generation's file.
  - §6.5 prune: keeps what the pointer names, any newer generation file that passes Load's steps 1 and 2, and their
    blobs, and deletes generation files before blobs. It runs only after an `INSTALLED` sync install whose pointer read
    `Found` before it with every generation it named loading through step 2, never after a seed load at `start()`, a
    heal flip or at `start()`. It deletes nothing when the pointer, or a generation it names, does not read.
  - §7.1: the `_since` cursor is sent only while the pointer also names the live generation, so a 304 never leaves a
    pointer that does not name what is served unhealed.
  - §6.5 the generation file reads only as its own canonical bytes; prune deletes nothing when any read it makes throws;
    the adopt scan never counts twice a generation the start's chain already failed to load.
  - §5.1: a pointer, or a `live`, that does not pass Load's steps 1 and 2 at `start()` counts `storeFailures` with no
    warning; `STORE_UNREADABLE` means only the in-memory fallback.
  - §6.5 crash recovery: the chain decides on each candidate's `<ts>` against the seed's and loads only the winner.
  - §6.5 the seed-load rule: (a) needs a `live` that passes steps 1 and 2. (b)'s adopt scan runs over
    `generations/*`, newest first, ties by name, re-verifying the signature under the seed's leaf. No seed load at
    `start()` prunes or deletes.
  - §3, §4, §5.1, §8: an instance whose lock is held, whose store is unreadable, or that meets a newer layout under
    `IN_MEMORY` runs on `inMemory()` for the life of the process, with `STORE_LOCKED`, `STORE_UNREADABLE` or
    `STORE_NEWER_LAYOUT`, never retried. `RevoktState.readOnly`, `READONLY_POLL_INTERVAL`, promotion, the storage
    retry, and the `STORE_LOCKED` sync result go. `JvmStorage` fsyncs every store directory at open and the parent of
    each directory it creates, and sweeps its temp files at open.
  - §3.2, §7.3, §11: a stored generation's `index.bin` is rebuilt at load. §6.4: `MAX_CHANGESET_RECORDS` is 1,024.
  - test-plan.md §9.1: the store readers are fuzz targets, the generation file among them.
  - test-plan.md (e) and (f): the store and seed rows for the new layout, the crash rows and the in-memory second
    process.
