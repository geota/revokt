- **#147, the sync schedule on the loader:**
  - §5.1 Lifecycle: the start task runs the seed, then, with a fetching source, the first sync, then clears `pending`.
    The JVM join stays bounded by `awaitData`, so a slow first sync never holds `start()` (lead, 2026-11-23). §4
    `DataState.pending`, the §5.1 overload table and §8 now say "until the start task installs a generation or ends".
  - §5.1 "The sync schedule" (new): after a sync that did not fail, the next is at `POLL_INTERVAL` (6 h) plus a jitter
    uniform in `[0, POLL_JITTER)` (36 min), or the source's `backoffUntilMillis` when later. A `FAILED` sync waits its
    `backoffUntilMillis` exactly, a `SKIPPED`/`BACKOFF` one the backoff it honoured, and a sync that wrote no
    `updater.json` 15 min. Every delay is clamped to 60 s to 24 h, measured on `clock` and waited on the loader's
    monotonic timer. The task reschedules in a `finally` and rethrows a fatal error after that, logged at `ERROR`
    first, since the loader's task swallows it. A fatal error inside the timer's own `schedule` call ends polling
    (an accepted residual). The scheduled sync never re-opens the seed.
  - §5.1, §7.1: while the start task's store read is unresolved (the seed load's read threw, its install failed
    before `activate`, or it found a stored generation 0.2 does not load), every sync first re-runs the seed load and
    syncs only once the seed is live. Otherwise it fetches and writes nothing, and retries in 15 min (the #273 review,
    moved from #143).
  - §7.1: the cursor (`_since`, `If-None-Match`) is sent only while it equals the live generation's
    `sourceTimestampMillis`; otherwise the whole collection is fetched, so a 304 never leaves a fallback live (#205's
    review). Firefox keys `_since` on its local data's own timestamp.
  - §7.1: `MIN_POLL_DELAY` (60 s) floors every wait between two syncs, so `503` with `Retry-After: 0` cannot loop the
    loader. Firefox's update timer waits at least 120 s between two fires.
  - §8: once a sync's `updater.json` write records an attempt since the seed's install, the loader publishes the
    seed generation again with its `STALE` gate open and `generationEpoch++`.
  - §5.1 limits: `POLL_INTERVAL`, `POLL_JITTER` and `MIN_POLL_DELAY`, internal. No `DiagnosticCode` or `WarningCode`
    joins.
  - §11 0.2: the schedule and its internal seams (the loader's timer and the jitter's random source).
  - Appendix A: the #147 sources (Firefox's poll timer, backoff and conditional changeset; upki's `fetch`).
  - Test plan §9: the schedule's rows in data-path (a), the store re-read, the conditional request after a fallback,
    and the content-signature sequence through the schedule.
  - 0.3 note: with a persisted store, a sync that `close()` cuts off should write nothing to `updater.json`, so it is
    not a feed failure. Firefox starts no sync during shutdown and reports `SHUTDOWN_ERROR` for one it cuts off. In
    0.2 the cut-off sync's failure write lands in the in-memory store, which `close()` discards.
