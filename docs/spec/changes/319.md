- **#319, `_since` is the served generation's own `<ts>`:**
  - §7.1: a delta poll sends `_since=<ts>`, where `<ts>` is the served generation's, read from the same file as the merge base. It does so only while that file loads, its `<ts>` is the live generation's `sourceTimestampMillis`, and the pointer names it as `live`. The `updater.json` cursor is never sent. After a seed install, or a fallback to the seed while the cursor names a newer generation, the sync is a delta from the seed's `<ts>`, as Firefox's is from its dump's (`CrliteRuntimePollTest` "after a seed fallback the seed's ts is sent, never the cursor", "the first sync after a seed install sends the seed's ts with no If-None-Match"). A served file whose `<ts>` is not the snapshot's fetches the whole collection (`CrliteRuntimePollTest` "a served file whose ts is not the snapshot's sends no _since").
  - §7.1: `If-None-Match: "<ts>"` is sent only while `updater.json`'s cursor and watermark are at or past `<ts>`. While they are behind it, the changeset since `<ts>` verifies, and the `UNCHANGED` repair of §6.5 is written from it, never from an unsigned 304 (`CrliteDeltaSyncTest` "a cursor older than the live generation sends its ts with no If-None-Match", `CrliteDeltaBaseTest` "with no cursor the served ts is sent with no If-None-Match", `StoreCrashTest` row 4). This replaces the rule that sent `_since` only while the cursor equalled the live `<ts>` and otherwise fetched the whole collection.
  - §3 `FetchRequest`: `If-None-Match` is the quoted `<ts>` of the generation served, not the cursor. §6.5: the cursor is no longer the `_since` value, and the whole collection is the fetch with no `_since`. §7.1's private-mirror note now says the delta path carries over.
  - Appendix A: Firefox reads its merge base from the same database as its `_since` (`RemoteSettingsClient.sys.mjs` lines 747 to 749), takes the dump's timestamp after a dump import (lines 756 to 769), and verifies local data that has no metadata from `_fetchChangeset(expected, expected)` (lines 787 to 790).
  - `test-plan.md`: the #147 row and the #141 row state the new request.
