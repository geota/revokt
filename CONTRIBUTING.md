# Contributing to revokt

revokt, a Kotlin TLS revocation library, is not affiliated with Revokt (revokt.com).

This file is the rulebook: how work is picked up, how it is checked in, and what every gate enforces. The spec in
`docs/spec/revokt-spec.md` is the source of truth for behaviour; this file is the source of truth for process.
Agents read `AGENTS.md` first (it points back here). Governance is in `GOVERNANCE.md`.

## 1. Sources of truth and how they change

1. **The spec** (`docs/spec/revokt-spec.md`) is normative. The "Changes in revision N" blocks stay in the
   file as history. A code PR that implements a section says so with the `Spec:` trailer in its PR body.
2. **Spec changes are `spec` PRs**, reviewed like code, merged before the code that depends on them. A spec
   diff under 20 lines that is inseparable from its code may ride in the code PR, which then also carries
   the `kind/spec` label and the reviewer checks the spec diff against the three growability contracts
   (§4 Rule model, §3.2 engine seam, §11 milestones).
3. **ADRs** (`docs/adr/NNNN-title.md`, MADR format) record decisions the spec states but does not argue.
   The first four, accepted 2026-10-22:
   - ADR-0001 `PARSE_FAILED` and `ENGINE_ERROR` allow in `DEFAULT`; a flip is a later minor via the §4 grace rule.
   - ADR-0002 Two presets, `DEFAULT` and `STRICT`; `shadowPolicy` is the migration path, not a third preset.
   - ADR-0003 `revokt-engine` (multiplatform core) and `revokt-jsse` (JVM facade) stay separate artifacts through 0.3.
   - ADR-0004 The repository lives under the maintainer's personal account (§13 item 1) and uses only
     features that are free for public repositories there; the organisation-only features (merge queue,
     teams, the path-scoped required-reviewer rule) are replaced as section 7 states. Moving to an
     organisation not named "Revokt" is revisited when a third maintainer joins.
   - ADR-0005 **Solo-maintainer phase.** Until `MAINTAINERS.md` lists a second maintainer, no human can
     approve the maintainer's own PRs (GitHub forbids self-approval). Compensating controls, all enforced:
     rulesets require every status check but 0 approvals; every PR carries an **independent review** by a
     fresh-context agent pass (a review that did not write the code; its output is a PR comment under the
     heading `Independent review`, and PR-lint requires it); the maintainer reads the full diff before
     enabling auto-merge; the `cooling` check is **paused** (a hold for a second reader means nothing with one
     reader; it activates with the second maintainer); no release is cut and no
     `1.0` promise is made in this phase (§14 requires two release-capable maintainers and external review
     before 1.0). The phase ends, and the two-person rule of section 5 activates, in the PR that adds the
     second maintainer.
4. **Issues** are the unit of work (section 2). **Milestones** are `0.1`, `0.2`, `0.3`, `0.4`, `1.0`, as §11.
5. Nothing else is authoritative: not chat transcripts, not a PR description that disagrees with the spec,
   not a comment in code. When code and spec disagree, the spec wins and the code is the bug, unless a
   `spec` PR says otherwise. **Disagreement between maintainers**: the current spec text wins until a `spec`
   PR has the approvals section 5 requires; while there are two maintainers, the one `MAINTAINERS.md` names
   as lead for the current milestone breaks a tie and records it in an ADR.

## 2. How work is picked up

- **One issue per task.** A task issue has: an imperative title, the milestone, the spec sections it
  implements, the acceptance test (which §9 fixture ids, or which new fixture), its dependency issues, and
  labels from the fixed set below. A task issue without a spec reference gets `needs-spec` and is not picked
  up; `kind/ci`, `kind/build`, `kind/docs` and `kind/chore` issues cite the CONTRIBUTING section instead.
  Bug reports cite the failing test or the steps; triage adds the spec reference.
- **What is next is computed, not guessed.** `./gradlew specStatus` reads `docs/spec/revokt-spec.md` and
  the test tree and prints, per milestone: every §9 fixture id and §11 deliverable, whether a test or
  module implements it, and the open issue that claims it. Its output is committed as `docs/dev/status.md`
  and regenerated by CI (a stale file fails `check`, like the API dump). An agent or contributor picks the
  first unclaimed item on the critical path below; a maintainer's "Current focus" line at the top of
  `ROADMAP.md` overrides the order. (Adopted from PhotoCraft's ordered checklist: roadmap, gap list,
  measured scorecard, automated parity command.)
- **Claiming.** Collaborators assign themselves. Anyone else comments `/claim`; a workflow assigns the
  commenter (one assignee per issue). An issue idle for 14 days is unassigned by a maintainer. A PR that
  implements an open, unclaimed issue is still welcome; a PR that references no issue is closed by PR-lint
  with a template comment asking for one. PRs opened by Renovate are exempt from the issue-link and
  template-section checks; the completing maintainer adds the Trailers block (`Spec: none (deps)` and
  their `Signed-off-by`), which the `trailers` check still enforces.
- **Sizing.** A PR is reviewable: under about 400 net lines of **production source** (tests, fixtures,
  corpora and dumps excluded), one issue, everything that issue's acceptance test needs and nothing else, in
  whatever modules that takes. A size labeler adds `size/XL` above 400 and the PR must state the exception
  (the clubcard port's 1:1 translation files, generated API dumps, the bootstrap PR). Larger work is split
  into stacked issues (`part 1/3`).
- **Order.** §11 gives each milestone's scope; the critical path below and each issue's dependency list give
  the order. The 0.1 critical path: bootstrap PR (section 2, "Bootstrap") → `revokt-clubcard` port landing
  with recorded oracle goldens (the native oracle job that regenerates goldens follows it) → DER/TBS parser
  with the §9.2 oracle → `Rule` model and golden fixture → `index.bin` reader/writer and `GenerationFiles`
  → `RevocationEngine` and the Kotlin engine → `SymVerifier`, generator and reference walker → JSON and
  canonical JSON.
- **Bootstrap.** The first PR (build-logic, the module skeletons the milestone needs, the workflows, the
  gate configs, the repo files listed in GOVERNANCE.md) is exempt from the size rule, carries `Spec: none (bootstrap)`,
  and its Tests section says "build-logic TestKit tests only". Rulesets (Appendix B) are applied by a
  maintainer immediately after it merges and the exported JSON lands in the next PR. `build`, `ci`, `docs`
  and `chore` PRs may state `Tests: none, no behaviour change`, which PR-lint accepts for those types.
- **One task in flight.** The agent works on one issue and keeps one open draft at a time; a second issue
  starts when the first is merged, closed, or parked as `blocked` with a note. Contributors' PRs on the same
  file set as an open draft carry a note in both issues. When `main` moves, "require
  branches to be up to date" asks for an update before merge: use GitHub's **Update branch** button or merge
  `main` into the branch (the squash hides the merge commit); a rebase after review starts needs the
  reviewer's okay in the thread, since it is a force-push.
- **Draft early.** Open the PR as a draft on the first commit so CI runs; mark ready only when every required
  check is green. A first-time contributor's workflow runs need a maintainer's approval; ask in the PR if
  nothing has started within two days.
- **Labels (fixed set, applied by a labeler workflow from paths and the template):** `area/<module>`,
  `kind/{feat,fix,spec,test,ci,build,docs,chore}`, `security` (touches a protected path), `ai-assisted`,
  `needs-spec`, `blocked`, `good-first-issue`, `quarantine`, `size/XL`, `run/android` (triggers the emulator tier on a PR).

## 3. Repository conventions

**Layout** (one Gradle module per published §3 artifact; names are the artifact ids):

```
revokt/
  build-logic/                 included build: convention plugins (kmp-library, jvm-library, android-library, data-artifact) and the verification tasks below, with TestKit tests
  gradle/libs.versions.toml    the only place a version is written
  gradle/verification-metadata.xml, gradle/verification-keyring.keys   checksums and exported PGP keys (offline verification)
  gradle/*.lockfile, settings-gradle.lockfile, buildscript-gradle.lockfile, build-logic/**.lockfile
  revokt-clubcard/ revokt-engine/ revokt-jsse/ revokt-bc/ revokt-okhttp/ revokt-ktor-core/ revokt-ktor-*/
  revokt-android/ revokt-android-work/ revokt-testing/ revokt-bom/
  revokt-engine-upki/          included in settings only under -Prevokt.native (needs JDK 22; CI-only, never published)
  native/                      Cargo workspace (revokt-upki-shim, revokt-oracle) and the Go producer and zlint CLIs; NOT Gradle modules; the Rust crates built by the native CI job, the Go CLIs by their golden recorder
  consumers/                   maven-consumer, java-consumer, kotlin-consumer, android-consumer (the §3.1/§9 consumer builds; run under -Prevokt.ci)
  data/seed/                   the weekly seed job (publishes revokt-seed-<channel>; separate publishing identity, section 9)
  corpus/                      committed fixture corpora (small) with their SHA-256 manifest; the large corpus is the public revokt-corpus repository, pinned by tag + manifest
  docs/spec/ docs/adr/ docs/dev/
  LICENSE LICENSES/ NOTICE SECURITY.md MAINTAINERS.md GOVERNANCE.md CODEOWNERS CODE_OF_CONDUCT.md CONTRIBUTING.md AGENTS.md CLAUDE.md -> AGENTS.md REUSE.toml
```

The 0.1 bootstrap creates `build-logic`, `revokt-clubcard`, `revokt-engine`, `revokt-bom`, `consumers/` and
`native/`; the other modules, their `area/` labels and their CI jobs arrive with their milestone.

**`AGENTS.md` is a map, not a manual** (OpenAI's lesson; the GitHub study's "commands early, exact
boundaries, concrete examples"): section 0, the three boundary lists of section 12, the exact commands of
Appendix C, and a reading list into `docs/` (`docs/spec/`, `docs/adr/`, `docs/dev/status.md`,
`docs/dev/local.md`, `docs/dev/fixtures.md`). It grows by one rule: **when the same correction is given
twice, it is added to `AGENTS.md` in that PR.** Module-level `AGENTS.md` files exist only where a module's
commands or boundaries differ (`revokt-clubcard/AGENTS.md` for the MPL port rules, `native/AGENTS.md`).

**Toolchain (pinned; the scaffold facts).** Gradle 9.7 wrapper with `distributionSha256Sum` (the newest fully supported by the Kotlin Gradle plugin); Kotlin 2.4.21;
AGP 8.13.2 (Kotlin 2.4 supports up to AGP 9.3; the Android modules arrive in 0.3); JDKs from `actions/setup-java`, never
auto-provisioned (`org.gradle.java.installations.auto-download=false`, no foojay resolver); `jvmToolchain(21)`
to build, `-Xjdk-release=17` and `jvmTarget = 17` on every jvm module (spec revision 38; Android consumers dex it with
the AGP 8.5.2+ that Kotlin 2.4 already requires), `jvmToolchain(22)` only inside
`revokt-engine-upki`; `org.gradle.configuration-cache=true`, `org.gradle.caching=true` (local cache only;
no remote cache, section 7); `gradle/actions/setup-gradle`
with `cache-read-only` on every branch but `main`; Kotlin/Native's compiler distribution (downloaded by KGP
from JetBrains' CDN, outside lockfiles and verification metadata) cached under `~/.konan` by Kotlin version;
Robolectric `android-all` jars cached and `robolectric.offline=true`; runner images `ubuntu-24.04`, `macos-15`,
`windows-2025`; `.gitattributes` marks `corpus/` and fixtures `-text` so Windows checkouts hash identically.

**Language and style.**
- Formatting: **ktlint** with `ktlint_code_style = ktlint_official` in `.editorconfig` (stated explicitly,
  since IntelliJ's "official" style and ktlint's default differ); formatting is never a review topic, run
  `./gradlew ktlintFormat`. **detekt** for complexity, naming, forbidden APIs and the custom rules below;
  detekt-formatting is off and detekt style rules that overlap ktlint are disabled; committed config; **no
  baseline file, ever** (a detekt upgrade that adds rules is fixed in the upgrade PR or the new rule is
  configured off with a `kind/chore` follow-up issue; `size/XL` is acceptable for that PR).
- `explicitApi()` on every published module. `internal` by default; opt-in markers `@RevoktInternalApi`
  (error level) and `@RevoktTestingApi` (warning level) exactly as §3.1 and §4, both with `BINARY`
  retention (the API-dump tool filters on them).
- **Every custom rule's message is a remediation instruction** (OpenAI's practice: "the error message tells
  the agent how to fix it"): `Public constructor on final class dev.revokt.Foo: give it a private constructor
  and a nested Builder (CONTRIBUTING §3, spec §4), or add it to allowedClasses with a reason`, never a bare
  rule name. The same applies to the build-logic verification tasks and to `specStatus`.
- **Custom detekt rules** (a `revokt-detekt-rules` module inside build-logic, each with tests):
  - `PublicConstructorOnFinalClass`: a public constructor on a final, effectively-public class, exempting
    structurally: classes named `Builder`, classes whose supertype simple name ends in `Exception`/`Error`,
    `object`/`enum`/`annotation`/`fun interface`, declarations annotated with either opt-in marker, and a
    configured `allowedClasses` FQN list (the §4 service types: `KotlinRevocationEngine`, `JvmPlatformTrust`,
    `AndroidPlatformTrust`, `JcaSignatureVerifier`, `PkixPathBuilderFallback`, the `HttpFetcher.Factory`
    implementations, `RevoktSyncWorker`, `SymVerifier`). No type resolution, so it runs on commonMain.
  - `NoDataOrValueClassOnPublicSurface` on published modules (§4).
  - `ClubcardPortRules` in `…clubcard.port`: no `inline fun`, no `const val` (§3.1 item 5).
  - `ForbiddenImport` in a dedicated `detektCommonMain` task that the kmp-library plugin registers over
    `src/commonMain/kotlin` with `detekt-common.yml` (`java.*`, `javax.*`, `kotlin.jvm.Volatile`), no classpath,
    attached to `check`; a TestKit test asserts the task exists. This is the fast check; **the purity compile
    (`:revokt-engine:compileKotlinLinuxX64 -Prevokt.purityGate`) is the authoritative gate** (an FQN use
    without an import bypasses detekt); `-Prevokt.ci` sets `revokt.purityGate` as well, so `ci-extras` and
    a local `-Prevokt.ci` run include it. The purity job compiles only; `linuxX64Test` and the native test
    binary link are disabled by the convention plugin.
  - `NoHttpClientInTests`: `java.net.http.*`, `java.net.URL`, `java.net.HttpURLConnection`,
    `javax.net.ssl.HttpsURLConnection` forbidden in test sources outside `**/fetch/**` and the live checks
    (the project's loopback TLS fixtures, ours rather than the spec's, live under `fetch`); advisory, since
    the real no-network gate is the runner (section 6).
- **API-level safety for Android consumers**: **animal-sniffer** with the `gummy-bears-api-26` signature on
  every jvm module an Android module depends on (`revokt-engine-jvm`, `revokt-jsse`, `revokt-okhttp`,
  `revokt-ktor-*`), wired into `check`. This is what catches `completeAsync`, `List.of`, `readAllBytes`
  and `setAuthenticator`; Android lint only analyses a module's own sources, so lint `NewApi` stays fatal on
  the real Android modules (`revokt-android`, `revokt-android-work`, `consumers/android-consumer`) and is
  not the guard for the jvm modules.

**Licensing and headers.**
- Apache-2.0 everywhere except `revokt-clubcard` (MPL-2.0) and, if the §12 trigger fires, the upki pair.
- Every source file has an SPDX header (`SPDX-License-Identifier`, `SPDX-FileCopyrightText`); port files add
  the upstream provenance line (§3.1 item 2). `REUSE.toml` expresses the per-path licences; **`reuse lint`**
  runs on every PR; a build-logic task `verifyHeaderLocations` fails when an `MPL-2.0` header appears
  outside `revokt-clubcard/src/*/kotlin/**/port/**` (§3.1 item 3, the header-location rule).
- `verifyPomLicenses` (build-logic task on `check`) reads every publication's generated POM (KMP root and
  `-jvm` included): `revokt-clubcard` exactly `MPL-2.0`, everything else exactly `Apache-2.0` (§3.1 item 1).

**Dependencies.**
- Versions only in `libs.versions.toml`. **Locking**: `lockMode = STRICT`, every lockfile committed; a
  build-logic task `resolveAndLockAll` resolves every resolvable configuration so entries for the purity,
  native and Android configurations are not dropped; the recipe is one line, in `docs/dev/deps.md`:
  `./gradlew resolveAndLockAll --write-locks --write-verification-metadata sha256,pgp --export-keys -Prevokt.purityGate -Prevokt.native -Prevokt.ci --no-configuration-cache`.
- **Verification**: `verification-metadata.xml` (checksums and PGP) with the exported
  `verification-keyring.keys` committed, so verification is offline; `<trusted-artifacts>` for `-sources`
  and `-javadoc` jars so IDE sync works; the Gradle wrapper JAR is checked by `gradle/actions/wrapper-validation`.
  A new dependency's entries are part of the PR that adds it, and the reviewer checks a new trusted key's
  fingerprint against the upstream project's published key.
- **Updates**: Renovate, grouped weekly, pinned digests for Actions and Docker images, automerge off,
  `platformCommit` not needed (commit signing is not required, section 4). Renovate cannot regenerate
  lockfiles or verification metadata on the hosted plan, so **a maintainer completes every Renovate PR** by
  running the recipe above and pushing to the Renovate branch; if the project later self-hosts Renovate,
  that becomes a `postUpgradeTasks` step. (Dependabot now understands version catalogs too; Renovate is
  chosen for grouping and digest pinning.)
- `verifyDependencyScopes` (build-logic task on `check`) inspects the outgoing `apiElements`/`jvmApiElements`
  and `runtimeElements` variants: Okio and `revokt-clubcard` never in an api variant; kotlinx-coroutines in
  `revokt-engine`'s api variant; OkHttp, Ktor and bcprov only in their own binding (§3 "Dependency scopes").
- The dependency ingress files (`libs.versions.toml`, `verification-metadata.xml`, `verification-keyring.keys`,
  every lockfile, `renovate.json`, `.commitlintrc.cjs`, `REUSE.toml`, `detekt*.yml`) are CODEOWNERS paths.

**Generated and committed, on purpose.** API dumps from the standalone **Kotlin binary-compatibility
validator** (0.18.x: `apiDump`/`apiCheck`, `nonPublicMarkers`, Android library support, `klib { enabled = false }`
as §3's purity-gate paragraph; not the Kotlin Gradle plugin's still-experimental `checkKotlinAbi`),
lockfiles, verification metadata and keyring, corpus manifests, `docs/dev/status.md` (from `specStatus`),
Jazzer regression inputs (`src/test/resources/<pkg>/<Class>Inputs/`, the only location Jazzer reads),
`docs/dev/rulesets/*.json`. Everything else the build can produce is not committed (Scorecard
`Binary-Artifacts`): no jars, no `.so`, no generated sources, no reports. Corpora are data: small ones under
`corpus/` with their SHA-256 manifest (capped at a few MB); the large corpus is the **public** `revokt-corpus`
repository, checked out by CI at the manifest's pinned tag into `build/corpus`, cached by tag, and read by
the replay task from a Gradle property so a local run can skip it; `verifyCorpusManifest` always checks
`corpus/` against its manifest and checks `build/corpus` when the property is set.

**Oracles are tools, never shipped** (FilmCraft's rule for FFmpeg, stated for ours): `revokt-oracle`, the
Go producer CLI, `rust-query-crlite`, `clubcard-crlite` and the upki engine are test oracles and fixture
generators; nothing under `native/` or `revokt-engine-upki` is linked, bundled, published or reachable from
a published module's dependency graph, and `verifyDependencyScopes` asserts it.

**Ratchets never go down** (PhotoCraft's `FLOOR` rule): the count of implemented §9 fixture ids in
`docs/dev/status.md` may not decrease (`specStatus` fails `check` if it does, and the quarantine rule in
section 6 keeps fixture tests from being deleted); the Kover floors may only be raised; a removal from an
API dump needs `!` in the title; `MAX_*` limits in `RevoktLimits` change only through a `spec` PR.

## 4. Branches and commits

**Branching: trunk-based.** `main` is the only long-lived branch and is always releasable at the current
milestone's level. `release/0.x` branches exist only for backports (section 9) and are protected like `main`.
(kotlinx.coroutines uses `develop`; one branch with squash merges and "require up to date" keeps history
linear and the rulesets simple.)

Branch names: `<type>/<issue>-<slug>` (`feat/42-tbs-parser`). Branches are deleted on merge.

**Commits on a branch** are the contributor's business: `fixup!`/`squash!` commits are fine and disappear
at squash; every branch commit still carries the human `Signed-off-by` (`git commit -s`), because the DCO app
checks each one (it skips bot authors). A commit that builds on its own is a norm, not a gate. Never rewrite
`main`. Force-push on your own branch is fine before review starts; after a review comment, push fixups so
the reviewer sees the delta.

**What reaches `main` is the squash commit**, whose message GitHub builds from the PR title and the PR body
(repository setting "default to pull request title and description"; auto-merge uses it unchanged). The rules therefore apply
to the **PR title** (commitlint, Appendix A) and the **PR body's Trailers block** (PR-lint):

```
<type>(<scope>)!: <imperative description, ≤ 72 chars, no trailing period>

<PR body: What and Why; wrap is not enforced, URLs are fine>

Spec: §5.1, §9 (k)                       or   Spec: none (<one-line reason>)
Fixes: #42
BREAKING CHANGE: <only when a published API dump changes non-additively or a preset row changes>
Co-authored-by: <vendor model name and version> <vendor no-reply address>   (AI-assisted PRs, section 12)
Signed-off-by: Name <email>              (the human author's; copied from the branch commits)
```

- **Types** (closed set): `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`, `revert`,
  `spec`. `spec` is ours. `feat`/`fix` drive the changelog and SemVer; `!` or `BREAKING CHANGE` is required for
  a non-additive API-dump change or a preset-row change. GitHub's revert button produces `Revert "…"`; retitle
  it `revert(<scope>): …` with the reverted SHA in the body.
- **Scopes** (closed set): module short names (`clubcard`, `engine`, `jsse`, `bc`, `okhttp`, `ktor`, `android`,
  `work`, `testing`, `bom`, `oracle`, `upki`, `seed`) plus `repo`, `deps`, `release`, `consumers`.
- **`Spec:`** is required on `feat`, `fix`, `perf` and `refactor` with a module scope; for `repo`, `deps`,
  `release`, `consumers` scopes and for every other type it is `Spec: none (<reason>)` or absent. PR-lint
  enforces this from the PR body.
- **`Signed-off-by`** is the DCO (§3.1 item 9; we have no CLA). It is always a human's name and email, never
  an agent identity. A maintainer never adds a sign-off on a contributor's behalf; a PR whose author will not
  sign is closed and the change is reimplemented from the issue, not from the diff.
- **Commit signing is not required.** The squash commit is signed by GitHub's web-flow key on merge; requiring
  contributor signatures would add friction for outside contributors and agents while the signature on `main`
  would still be GitHub's. Maintainers enable vigilant mode on their accounts; release tags are signed by the
  release workflow with the release key (section 9).
- The `trailers` check (PR-lint, re-run on every `edited` and `synchronize` event) fails when the PR body
  lacks a trailer that any branch commit carries (`Co-authored-by`, `Signed-off-by`), so disclosure survives
  the squash.

## 5. Pull requests

**One PR = one issue = one logical change**, where the unit is the issue's acceptance test (section 2).
The template (`.github/PULL_REQUEST_TEMPLATE.md`) has mandatory sections; PR-lint fails when one is empty or
a trailer rule is violated:

1. **What** (one paragraph) and **Why** (link the issue).
2. **Spec**: sections implemented and "no observable behaviour outside the spec", or the `spec` PR link.
3. **Tests**: fixture ids or test names added or changed; for a bug, the test that failed first and the CI
   run or local command that showed it red (the squash hides the first commit, so the PR records it).
4. **API**: "no public API change" or the `api/*.api` diff summary and the `!` justification.
5. **Risk and rollout**: the §10 item touched, or "none"; any preset row, data format or `seedFormat` involved.
6. **AI assistance**: "none", or which parts an agent wrote (sets the `ai-assisted` label).
7. **Checklist**: spec cited · tests added · `./gradlew check` green locally (or which part was skipped and
   why) · API dump updated · headers present · dependency entries added · fuzz target added for any new parser.
8. **Trailers** block, **last in the template** (PR-lint checks it is last), which GitHub copies verbatim
   into the squash body with the rest of the description, so `git interpret-trailers` parses them. The
   squash subject is the PR title plus ` (#N)`, so it runs to about 80 characters; the 72-character limit
   applies to the PR title.

**Review rules.**
- **The two-person rule (§14) is: the author plus one approving maintainer who is a code owner of every
  protected path the PR touches, and neither of them is an agent.** GitHub's "require review from code
  owners" is satisfied by one owner's approval; every maintainer is listed by handle in `CODEOWNERS` for the
  protected paths (collaborators with write access, since a personal account has no teams), and the author
  cannot approve their own PR, so with two maintainers this is exactly what GitHub enforces. The
  path-scoped required-reviewer ruleset rule is organisation-only, so a small Action (`protected-paths`)
  reads `MAINTAINERS.md` and the changed paths and fails until the required number of **maintainer**
  approvals is present: one while `MAINTAINERS.md` lists two, two for PRs whose author is not a maintainer
  once it lists three or more; it passes at once when no protected path changed, and during the
  solo-maintainer phase (ADR-0005) it requires nothing (0 approvals) and `pr-lint` requires the `Independent review` comment instead.
  It reads `MAINTAINERS.md` and `.github/protected-paths.txt` **from the base branch**
  (`ref: ${{ github.event.pull_request.base.sha }}`), never from the PR head, so a PR cannot add its author
  to the list or shrink the paths; it runs on `pull_request` (`opened`, `synchronize`, `reopened`) and
  `pull_request_review` (`submitted`, `dismissed`) with `contents: read` and `pull-requests: read`, and it
  never counts an approval from the handle that the head commits' `Signed-off-by` names. Stated plainly:
  while two maintainers exist the Action adds nothing GitHub does not already enforce through code-owner
  review; it becomes a boundary at three.
- Protected paths (CODEOWNERS and the `protected-paths` Action, one list, kept in `.github/protected-paths.txt`): `revokt-clubcard/**`,
  `**/verify/**`, `**/walker/**`, `**/RevoktTrustManager*`, `**/parser/**`, `**/fetch/**`, `**/signature/**`,
  `data/seed/**`, `.github/**`, `build-logic/**`, the dependency ingress files (section 3), `docs/spec/**`.
- Ordinary paths: one maintainer approval (0 during the solo-maintainer phase, ADR-0005, where the
  `Independent review` comment and the maintainer's own full read of the diff stand in). The author never
  approves their own PR. Agent review comments are advisory once a second maintainer exists; the human
  approval is the only approval. "Require approval of the most recent
  reviewable push" is on, so a push after approval re-requests it.
- Every review thread is resolved before merge (fixed, or declined with a reason the reviewer accepts).
- Reviewers review against the spec first, then the code; a reviewer who finds the spec wrong asks for a
  `spec` PR rather than approving a quiet divergence.
- **Merge: squash only, by auto-merge** ("require branches to be up to date before merging" is on, so the
  required checks always ran against the current `main`; a maintainer enables auto-merge after approving
  and GitHub merges when the checks pass). Linear history required. **The cost of having no merge queue,
  stated honestly**: when `main` moves under an approved PR, "Update branch" (or a merge-base change) dismisses
  the approval as stale, the full required-check matrix reruns, and a maintainer re-approves before auto-merge
  fires. Mitigations: approve and enable auto-merge one PR at a time on a busy day; the **author** updates the
  branch, not the reviewer; on fork PRs "allow edits from maintainers" must be on for a maintainer to update
  it at all. "Require approval of the most recent reviewable push" stays on (it is the control that makes a
  late push by the author visible).
- Stale: a draft idle for 30 days is closed with a note unless labelled `blocked`; the branch stays.
- **Triage SLA**: every new issue and PR gets a maintainer label or comment within 7 days; an outside PR gets
  a first review within 14 days or a dated note saying when.

## 6. Verification and testing

The spec's §9 tiers are the CI tiers. **What a PR can break, a PR must test; what only the nightly can test,
the nightly blocks the release.**

**The local gate.** `./gradlew check` is **JDK-only and offline**: unit tests, committed fixtures and the
corpus replay with recorded oracle goldens (§9.2 D1–D3 and D8 offline), Jazzer regression inputs (`JAZZER_FUZZ`
unset), the `Rule`/precedence/golden-fixture tests, ktlint, detekt (including `detektCommonMain`),
`apiCheck`, animal-sniffer, `verifyPomLicenses`, `verifyDependencyScopes`, `verifyHeaderLocations`,
`verifyCorpusManifest` and the Kover per-package floors. It needs no Android SDK, no Rust, no Go, no network.
`-Prevokt.ci` adds the Android modules (lint `NewApi` fatal, Robolectric tests), the consumer builds
(`consumers/*`; the Maven one runs `publishToMavenLocal` then `mvn -B verify`, online until `~/.m2` is pre-seeded) and the
purity compile; `-Prevokt.native` adds `revokt-engine-upki` (JDK 22) and the native builds. The full local
approximation of a PR run is `./gradlew check -Prevokt.ci` plus `reuse lint`, `actionlint` and
`npx commitlint` on the intended title; measured durations are published in `docs/dev/local.md` after the
bootstrap. If a local tool is missing, say so in the PR and push; **CI is authoritative, and "green" means
every required check in Appendix B passes**.

**Every PR (required checks, offline except where noted):**
- `check` on JDK 17, 21, the current LTS and the current feature release (Linux; §9.2 matrix), with the
  Conscrypt dimension inside each job (the replay test task runs once per Conscrypt uber version listed in
  the committed matrix file, selected by `-Prevokt.conscrypt=<version>`); Kover instrumentation only on the
  JDK 21 job; `check` on JDK 21 on macOS and Windows for `revokt-engine` and `revokt-jsse` only (file
  locking, `ATOMIC_MOVE`).
- `ci-extras` on Linux/JDK 21: `-Prevokt.ci` (Android lint and Robolectric from 0.3, consumer builds, purity).
- Static (the `static` job): `reuse lint`, `actionlint` (actions pinned by SHA; top-level
  `permissions: read-all`; no `pull_request_target` with checkout), wrapper validation, labeler. As their
  own checks: `commitlint` on the title; `pr-lint` (template, trailers, `Spec:` rule, issue link,
  `Independent review` comment in the solo phase; runs on `opened`, `edited`, `synchronize`);
  `protected-paths`; `cooling` (section 8; green at once for other paths, and throughout the solo phase); `DCO` (the app's check). ktlint,
  detekt and `specStatus` run inside `check`.
- Security: CodeQL in its own job (Kotlin needs a traced build; it compiles `compileKotlinJvm`
  `compileDebugKotlin` without tests, on its own budget; when a Kotlin bump leaves CodeQL's supported window,
  the `kind/ci` PR that bumps Kotlin sets CodeQL `continue-on-error` with an expiry issue), OSV-Scanner on
  the lockfiles (needs network; an unfixable finding is allow-listed in `osv-scanner.toml` with an expiry
  date), `dependency-review-action` with a licence allow-list, secret scanning with push protection
  (repository setting).
- **No network in the test jobs**: `step-security/harden-runner` with `egress-policy: block` on the Linux
  jobs (loopback allowed, so the project's loopback TLS fixtures run; it must be the first step, so caches
  are warmed by a separate job whose outputs the test job restores). harden-runner is audit-only on macOS
  and Windows, so those two jobs run Gradle `--offline` after cache restore and rely on `NoHttpClientInTests`;
  the table marks them advisory.
- Coverage: Kover branch floor of 90 % per parser package over the committed replay (§9.1), as a hard rule;
  overall line coverage compared against the `main` artifact (`coverage-main`, the Kover XML uploaded from
  `main`) by a script in `build-logic`: not below the `main` value, with the 90 % target reached by 0.2.

**Nightly and on release branches (blocking for a release, informational on `main`):**
- The native job: builds `native/` (Rust cdylib, Go CLI) and `revokt-engine-upki`, runs the §9 oracles, the
  end-to-end CRLite oracle over the pinned corpus, the cross-engine suite (0.2+), and regenerates oracle
  goldens for corpus admission.
- The producer job (spec §9.2; weekly, on every producer, certificate-transparency-go, zcrypto or Go pin change, and
  before each release): oracle 4 at the pin and at `mozilla/crlite` `main` over the union corpus, plus at least
  100 000 fresh CT entries; publishes the D8 gap by clause.
- Fuzzing: ClusterFuzzLite batch matrix, one job per §9.1 target, `base-builder-jvm` pinned by digest, the
  coverage cron and the corpus storage token configured, corpus merged back weekly; a crash is uploaded as a
  SARIF artifact and a workflow step files the `security` issue (ClusterFuzzLite does not file issues itself).
- Android emulator matrix (API 26, 31, 34, 36) on hosted Linux runners with KVM, from the mirrored system
  images (§11), including the null-host probe, the StrictMode main-thread probe and the API-26 futures
  fixture; triggered by schedule, `workflow_dispatch`, and the `run/android` label on a PR. Robolectric on the
  PR tier covers storage directories, WorkManager scheduling (`WorkManagerTestInitHelper`) and the lifecycle
  observer only; every trust-manager, parser, Conscrypt and StrictMode assertion is emulator-only.
- Minified-build tests (R8 with the shipped consumer rules) and the reproducible-build check (two clean
  builds on different runner images and dates, byte-identical jars), SBOM generation.
- **Benchmarks on the physical ARM device live in a private sibling repository** (`revokt-bench`, same
  account): a personal account has no runner groups, and a self-hosted runner attached to a public
  repository is reachable by any fork's `pull_request` workflow, which GitHub's own hardening guide says
  "should almost never" be done. `revokt-bench` checks out the public repository at the nightly SHA on a
  schedule, runs on an ephemeral runner the device starts from its own cron only during the nightly window,
  holds no secrets, and publishes the numbers back as a commit to `perf/baseline.json` through a PR on the
  public repository. Private repositories may use self-hosted runners at no cost.
- Live checks (Remote Settings reachability, filter size versus `CAP_NEAR_LIMIT`) are informational only.

**Test conventions.**
- Names: with a §9 fixture, `` `<§9 list> (<id>) <behaviour>` `` (`` `walker (k) same-key decoy with garbage signature` ``;
  the list name disambiguates §9's several lettered lists); without one, `` `<area> <behaviour>` ``. Kotlin
  backtick names in test sources; no `@DisplayName`.
- **A bug fix starts with the failing test** (first commit red, second commit green; the PR's Tests section
  names the red run). A fix without a test needs a maintainer's written exception in the PR.
- Determinism: no wall clock (`Clock`/`TimeSource` injected, §4), no network (the runner enforces it), seeded
  randomness with the seed printed on failure, no sleeps.
- **Flaky tests.** A test that fails twice without a code change is quarantined the same day. The process: the
  person or agent who hits it re-runs the job once; on the second failure they open a `quarantine` issue with
  both run links and say so in the PR; **the tag is applied by a maintainer, or in a separate
  `test(<scope>): quarantine <name>` PR, never inside the feature PR** (that would be weakening a gate). A
  quarantined test is excluded from the gate and listed in every CI summary. One that carries a §9 fixture id
  is **never deleted**: after 14 days it blocks the next release instead. One without a fixture id is fixed or
  deleted within 14 days with a maintainer's written reason.
- Every parser or decoder that reads bytes it did not produce has a Jazzer `@FuzzTest` (JUnit ≥ 5.9) with the
  static `fuzzerTestOneInput` wrapper for ClusterFuzzLite in the same PR (§9.1), and registering it in the
  ClusterFuzzLite matrix is part of that issue.
- Differential oracles record goldens at corpus admission (§9.2 schema), so PRs never need Rust or Go.
- **Garbage-collection pass** (OpenAI's practice against "functionally correct but poorly maintainable"
  agent code): the last issue of every milestone is a `kind/chore` pass over the modules the milestone
  touched, run by the agent in a fresh context with the brief "simplify, deduplicate, delete dead code;
  change no observable behaviour", delivered as one PR with no `feat` or `fix` inside and reviewed like any other.

**Definition of done for a PR:** spec cited and matched · tests per the rules above · every required check
green · API dump diff reviewed · `docs/dev/status.md` regenerated · changelog entry implied by the title ·
approvals per section 5 · threads resolved · squash-merged by auto-merge. Done means merged.

**Everything above is free for a public repository on a personal account**: rulesets, CODEOWNERS,
environments with required reviewers and deployment-branch limits, tag rulesets, unlimited Actions minutes
on standard Linux, macOS, Windows and Linux-ARM runners, self-hosted runners, GitHub Apps owned by the
account, CodeQL, secret scanning with push protection, dependency graph and `dependency-review-action`,
private vulnerability reporting and advisories with temporary private forks, artifact attestations on public
repositories, the DCO app, Mend's hosted Renovate, OSV-Scanner, Scorecard, ClusterFuzzLite (corpus in a
storage repository, no cloud bucket), Sigstore's public instance and Central Portal publishing. **Not
available on a personal account and therefore not relied on**: the merge queue, teams, the path-scoped
required-reviewer rule, "restrict who can push" by team, and larger hosted runners; paid services (Develocity,
a remote build cache, cloud fuzzing storage) are not used. If the project moves to an organisation later
(ADR-0004), the merge queue and the required-reviewer rule replace auto-merge and the `protected-paths` Action
with no change to the rules themselves. **What a personal account cannot prevent**: the owner can edit or
disable a ruleset, change merge settings, edit environment reviewers and secrets, remove a collaborator,
uninstall an app, or delete the repository. The second maintainer's protection is therefore the public audit
trail (the exported rulesets JSON and the weekly export-and-diff workflow above), the release key custody
split (section 9), and the fact that every one of those actions is visible to anyone with read access.

**Red `main`.** A failing required check on `main` is reverted first and investigated second; nothing
merges onto red `main` except the revert. An external-service failure (OSV database, CodeQL outage) is
handled by a time-boxed allow-list entry with an expiry date, in a `kind/ci` PR.

## 8. Security-sensitive paths and embargoed fixes

Protected paths (section 5) additionally require: the `security` label (auto-applied); the "Risk" section
naming the §10 item or "none"; a fuzz target for any new byte parser; and, for `data/seed/**`, the release
workflows and `**/verify/**`, the 24-hour `cooling` check and a **verification note** comment in the PR from
one maintainer to the other naming what was verified. In the solo-maintainer phase (ADR-0005) the cooling check is
paused and the note is the maintainer's own.

**Embargoed security fixes** are developed in a GitHub security advisory's temporary private fork, where
Actions do not run and rulesets are not enforced. The written exception: both maintainers run
`./gradlew check -Prevokt.ci` locally and record the head SHA and their run output in the advisory; the same
two-person review applies in the advisory; the fix is merged through the advisory flow as one squash commit
with the trailers; the post-merge CI run on `main` must be green before the release that ships it; the
bypass is recorded in the advisory. `SECURITY.md` carries the 90-day disclosure policy (§14), the private
reporting channel (GitHub private vulnerability reporting on), and the consumer verification recipe (the
PGP fingerprint, a Gradle `trusted-key` snippet, `gh attestation verify`).

## 9. Releases, data artifacts and versioning

- SemVer; `0.x` until M2 (§11); deprecation `WARNING → ERROR → removal in a major` (§11), restated here so a
  contributor reading only this file sees it. Tags `vX.Y.Z` under a tag ruleset (only the release workflow
  creates them). **Backports**: security fixes only, to the latest `0.x` minor; after 1.0, to the latest
  minor of the previous major for 12 months, through `release/*` branches protected like `main`.
- **Release workflow** (never by hand): `workflow_dispatch` by a maintainer on `main` → build on the pinned
  toolchain → `apiCheck` and the golden-fixture diff rule (§4 growability) → reproducible-build check → SBOM →
  **`release` environment**, whose required reviewers are both maintainers with "Prevent self-review" on
  (so the one who did not dispatch must approve) and whose deployment branches are `main` and `v*` → signed tag creation by `revokt-release[bot]` (a GitHub App owned by the account with
  contents permission only, the sole bypass actor of the `v*` tag ruleset; the tag is signed with the release
  key) → PGP signing and attestations (`id-token: write` and
  `attestations: write` only in the publish job) → Central Portal upload with `publishingType = USER_MANAGED`,
  so a second human presses Publish in the portal after checking the staged artefacts' hashes against the
  attestation (the namespace is a Central Portal organisation with both maintainers as members, so both can
  see the staged deployment; a Portal deployment is otherwise visible only to its uploader) → GitHub
  release with the changelog, the jars, `.asc`, `.sigstore.json` and provenance attached.
- **Central Portal publishing is a user token plus a PGP key** (no OIDC trusted publishing exists for the
  Portal; the spec's §10 and §14 say so since rev32). Both live only as `release`-environment secrets. **Key
  custody** (in `MAINTAINERS.md`): one release key generated offline, fingerprint published in `SECURITY.md`
  and on a keyserver, held by both maintainers, rotated at each major or on any suspicion, revocation
  certificate held by the second maintainer; the Portal token belongs to a Portal account that holds only
  this namespace (tokens are per account, not per namespace) and is rotated with the key.
- **Changelog** generated from the Conventional Commits titles (git-cliff with the custom `spec` type) and
  **hand-edited only to add** the notes the spec requires: every preset-row flip (§4), every `exemptable`
  change, every data-format or `store.version` change, every `seedFormat` bump. Each release also states
  its **AI-authorship figure** (Aider's practice): the share of merged PRs carrying `Co-authored-by` and the
  share of new lines from those PRs by `git blame`, with formatting commits in `.git-blame-ignore-revs`.
- **Data artifacts** (`revokt-seed-*`) are published by the weekly job under a **separate Portal account owning
  only the data namespace**, through its own `seed-publish` environment; the job verifies Mozilla's content
  signature before packaging (§7.1 verification, §6.5 archive layout), records the Remote Settings changeset timestamp, the record ids and each
  attachment's SHA-256 in the attestation, and smoke-loads the published artefact with the oldest supported
  engine minor before announcing it. Never in the BOM (§7.2); its workflow has its own CODEOWNERS entry.
- The `0.x` promise: no compatibility promise before 1.0, but the API dumps are committed and every
  non-additive diff needs `!`, so the history shows every break on purpose.

## 11. Where we depart from the reference repos, and why

- OkHttp and Okio reject LLM-assisted contributions outright. revokt accepts them **with disclosure** and
  human ownership (section 12), because the codebase is built with agents from day one and hiding that
  would make the public history dishonest.
- kotlinx.coroutines uses a `develop` branch; we use trunk-based `main` with squash auto-merge.
- OkHttp runs Spotless; we run ktlint and detekt with committed config and custom rules, and make both blocking.
- Many projects require signed commits; we require the DCO and not signatures (section 4), since the
  commit on `main` is GitHub-signed either way.
- Square and JetBrains keep their repositories under organisations; revokt starts under a personal account
  (§13, ADR-0004), which costs the merge queue and teams and nothing else that matters at two maintainers.

### Appendix C. Local workflow (`docs/dev/local.md`)
